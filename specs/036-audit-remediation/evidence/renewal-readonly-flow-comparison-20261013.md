## Findings and recommended work

1. **Current operational failure, high priority:** the supplied 00:18–00:27 Worker excerpts stop immediately after Sell Packages GET with `Load failed: PACKAGE_QUOTE_CHANGED`; there is no type-selection POST in those excerpts. The pre-repair resolver expected a bare `CISCO`/`IRDETO` label while the real form prefixes `Smartcard:`. This explains those *specific loading failures*, not the older wrong-package incidents. The current local source/95 focused tests include the repair, but the running server's Worker artifact was not inspected after commit `374ab91`. Compare every PM2 Worker source/build hash and restart all from one verified release before claiming the repeated failure is gone. Do not interpret BullMQ's “job completed successfully” as business completion; the handled job may have written a failed operation.
2. **Safe false-negative boundary, high priority for completion rate:** `rowMatchesTarget` requires the report's **Contract Start** to equal the Cairo day when Pay began. A valid scheduled start or extension can therefore fail automatic matching even if the invoice/package is correct. The report offers no distinct sale timestamp. Keep the review hold; improve correlation only after a provider-backed rule establishes which contract dates can follow a sale, with tests for future start and renewal extension.
3. **Safe false-negative boundary under outside activity:** `correlateRenewalFulfillment` treats more than one new report row, even an unrelated external sale on the account, as `UNEXPECTED_ACCOUNT_ACTIVITY`/proof conflict. The live report confirms the dealer is an account-wide sales view. This protects against misattribution but can put a correct transaction into review if the account is also used outside the panel. Confirm account exclusivity or design a unique-invoice attribution rule using complete before/after evidence; never accept a candidate by amount alone.
4. **STB provenance and logs:** `checkCard` ends with a fallback to any 15-digit number in page text and returns success even without a proven card-to-STB association. It also logs full card/STB and input values; the supplied production excerpts contain them. Prefer the explicit paired-STB element/label, validate association to the requested card, treat ambiguous/missing STB as unavailable, and redact identifiers and promo codes in Worker logs. This is a source risk and privacy improvement, not an observed wrong-STB sale.
5. **Live acceptance still required:** current browser evidence covers Check, CISCO package loading and Sold Report reading. IRDETO's completed input sequence, promo outcome, Add/Sell/STB/OK/Pay forms, and a newly sold invoice's exact relation to one panel operation were not observed. Local fixtures/test PASS cannot close those provider/release gates. No real transaction should be performed as part of this review.
